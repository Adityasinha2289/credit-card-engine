# RENO CRED 2.0 — MIGRATION BASELINE & IDENTITY RECONCILIATION

## Executive Summary
This report analyzes the discrepancy between the remote Supabase database and local migration files. The fundamental finding is that **`20260726000000_production_schema.sql` was an architectural draft that was never deployed to production**. The active application and remote database are running entirely on the older V1 schema (`001` through `004`). Because the V1 schema uses a `users` table instead of a `profiles` table, the newly proposed `20260809130000_commerce_schema.sql` (which references `profiles`) is incompatible with reality and must be refactored before deployment. 

## Actual Remote Architecture
The remote database is running the schema generated by `001_initial_schema.sql` and `002_full_persistence.sql`.
Key tables actively in use:
- `users` (Identity)
- `cards` (Catalog)
- `user_cards` (Wallet)
- `transactions`
- `credit_accounts`, `budgets`, `subscriptions`
- `apply_clicks`, `score_history`, `notifications`

## Local Migration Architecture
The repository contains two conflicting architectural visions:
1. **Migrations `001` - `004`**: The legacy V1 schema (currently live in production).
2. **Migration `20260726000000`**: A complete, parallel V2 architecture that proposed renaming `users` to `profiles`, and `cards` to `credit_cards_catalog`. It creates an entirely disconnected parallel data structure.

## Identity Architecture
Through codebase auditing (`src/features/dashboard/store/dashboardStore.ts`), we identified the application's actual identity flow:
1. **Clerk ID:** Clerk issues a string user ID (e.g. `user_2...`).
2. **Application Write:** `dashboardStore` explicitly writes `user.id` to the **`users`** table (`.from('users').upsert({ id: user.id, ... })`).
3. **RLS Identification:** RLS identifies the authenticated user via `auth.jwt()->>'sub'`, which perfectly matches the Clerk user ID stored in `users(id)`.
4. **Canonical Table:** `users` (NOT `profiles`).

## Migration-by-Migration Comparison
| Feature | Local 20260726 | Remote Database | Match |
|---|---|---|---|
| Identity Table | `profiles` | `users` | **DIFFERENT** (Critical) |
| Catalog Table | `credit_cards_catalog`| `cards` | **DIFFERENT** |
| Wallet Table | `user_cards` | `user_cards` | MATCH |

**Conclusion:** `20260726000000` is **Scenario D**: A replacement architecture that was NEVER deployed. 

## Why Migration History Is Empty
The `001_initial_schema.sql` explicitly states at the top: `Run this in: Supabase Dashboard → SQL Editor`. The original developers simply copy-pasted migrations `001` through `004` directly into the Supabase UI instead of executing `npx supabase db push`. Because the CLI wasn't used, Supabase never recorded them in the `supabase_migrations.schema_migrations` tracking table.

## Destructive Migration Risks
Applying `npx supabase db push` blindly will execute `001_initial_schema.sql` which starts with:
```sql
DROP TABLE IF EXISTS apply_clicks CASCADE;
DROP TABLE IF EXISTS transactions CASCADE;
DROP TABLE IF EXISTS user_cards CASCADE;
DROP TABLE IF EXISTS users CASCADE;
```
This would instantly delete the entire production database. 

## Recommended Baseline Strategy
**Strategy A:** Treat the current remote database (`users`, `cards`, etc.) as the production baseline. We must ignore `20260726000000` entirely as it is a dead, un-deployed architecture that would just create unused tables. 

## Required Commerce Schema Changes
Before we can deploy `20260809130000_commerce_schema.sql`, we must modify it to respect the actual production identity model:
1. Change `user_id TEXT NOT NULL REFERENCES profiles(id)` to `user_id TEXT NOT NULL REFERENCES users(id)` in `payment_methods`.
2. Change `user_id TEXT NOT NULL REFERENCES profiles(id)` to `user_id TEXT NOT NULL REFERENCES users(id)` in `tracking_events`.

## RLS Strategy
The existing RLS correctly uses `(auth.jwt()->>'sub') = user_id`. We will keep this exactly the same for `payment_methods` and `tracking_events`.

## Payment Method Identity Strategy
`payment_methods.user_id` must be defined as `TEXT NOT NULL REFERENCES users(id) ON DELETE CASCADE`.

## Tracking Identity Strategy
`tracking_events.user_id` must be defined as `TEXT NOT NULL REFERENCES users(id) ON DELETE CASCADE`.

## Exact Safe Execution Sequence
1. **Baseline Migration Tracking:** Run `npx supabase migration repair --status applied 001 002 003 004` to prevent their execution.
2. **Ignore Orphan Schema:** Run `npx supabase migration repair --status applied 20260726000000` (or simply delete the file) so Supabase ignores the un-deployed parallel architecture.
3. **Refactor Commerce Schema:** Update `20260809130000_commerce_schema.sql` to reference `users(id)` instead of `profiles(id)`.
4. **Apply Commerce Migration:** Run `npx supabase db push` to push only `20260809`.
5. **Verify:** Check remote schema and RLS policies.
6. **Seed Data:** Move to Phase 5D.2.

## Rollback Strategy
If `20260809` fails, we simply drop the new commerce tables. Existing systems (`users`, `user_cards`, `transactions`) remain completely untouched.

## Risks
If the `migration repair` step is done incorrectly, Supabase could still attempt to run `001` and drop the production database. Extreme caution is required during step 1.
